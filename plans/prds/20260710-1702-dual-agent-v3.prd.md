## Problem

### Product Direction

AiphaBee needs two independent decisions for an Agent request:

```text
selected_layer         = generic | research
selected_runner_family = edge | fastclaw
```

Layer determines permitted tools and data. Runner family determines how an
already-authorised request executes. A paid user is not automatically routed to
FastClaw, and FastClaw never upgrades Generic permission to Research.

The repository already owns the run/event/tool contract in
`@aiphabee/agent-runtime` and the public `/agent/*` surface in Worker. FastClaw
must fit behind those authorities. The product gap is a personal execution path:
one durable identity/profile for an entitled user, temporary isolated compute
for active work, and AiphaBee-owned durable records around it.

- Hard Constraints:
  - `@aiphabee/agent-runtime` remains the only run/event/tool authority.
  - Worker `/agent/*` remains the only public Agent API family.
  - Generic/Research policy is evaluated before runner dispatch and again before
    every tool call.
  - One active user/tenant maps to at most one active dedicated FastClaw
    identity/profile under the product contract.
  - A sandbox is ephemeral per run/session and is destroyed on success, failure,
    cancellation, timeout, or kill.
  - No shared-personal-Agent fallback exists.
  - Sandbox egress and credentials are deny-by-default and job scoped.
  - Durable memory and approved artifacts return to AiphaBee-owned storage.
  - Fixture-only tests cannot satisfy the live release gate.
- Recommended Defaults:
  - Keep runner registration and selection in the existing Agent Runtime.
  - Keep `workflow`, queue, and cron as triggers/orchestration rather than runner
    values.
  - Put the provider-neutral sandbox port beside the existing Agent Runner
    authority until a real second implementation justifies a separate package.
  - Use the approved Cloudflare sandbox direction for the first live backend,
    with the exact SDK/image pinned and revalidated during its execution row.
- Freedoms:
  - The runtime may represent product execution family through a strict runner
    registry, typed runner identifier, or equivalent single authority, provided
    it does not duplicate `AgentRunMode` semantics.
  - Identity persistence may extend an existing account/Agent table or introduce
    a focused table after the data-model slice proves ownership and lifecycle.

### Feasibility Boundary

- Confirmed:

  - Worker validates layer/mode and rejects run modes that have no enabled

## Acceptance Scenarios

### Scenario 1: Ordinary Paid Request Stays Generic and Edge

- Given: an entitled paid user asks for a standard company profile using only
  Generic-permitted tools.
- When: layer and runner-family routing is evaluated.
- Then: the request may select `generic + edge`; payment does not force FastClaw.
- Machine-checkable evidence: routing fixture asserts selected layer/family and
  absence of FastClaw provisioning or sandbox calls.

### Scenario 2: Personal Custom Research Uses Research and FastClaw

- Given: an entitled user requests permitted custom Python analysis requiring
  personal state and Research-only tools.
- When: policy, entitlement, budget, and runner availability pass.
- Then: the request selects `research + fastclaw`, uses only approved tools
  through Tool Gateway, and emits AiphaBee semantic events.
- Machine-checkable evidence: integration fixture asserts policy decision,
  runner selection, scoped token, event sequence, evidence validation, and final
  artifact ownership.

### Scenario 3: Runner Never Upgrades Capability

- Given: a Generic request asks for a Research-only tool while FastClaw is
  available.
- When: tool policy runs.
- Then: the request is denied before execution; changing runner family cannot
  make it valid.
- Machine-checkable evidence: policy/runner matrix tests cover all four
  layer-family combinations and deny the invalid request.

### Scenario 4: Provisioning Is Idempotent and Fail-Closed

- Given: two concurrent requests attempt to provision the same entitled
  user/tenant and the upstream partially fails.
- When: provisioning executes with the same ownership key.
- Then: at most one active identity exists; the other request observes the same
  result or a retryable blocked state; no shared identity is selected.
- Machine-checkable evidence: concurrent fixture, unique ownership constraint,
  retry state, and upstream call-count assertion.

### Scenario 5: Every Terminal Path Destroys Compute

- Given: sandbox runs covering success, execution error, client cancellation,
  soft timeout, hard timeout, and kill switch.
- When: each run terminates.
- Then: destroy is attempted exactly once through an idempotent cleanup path,
  residual handles/files are absent, billing reflects actual execution, and a
  terminal audit event is recorded.
- Machine-checkable evidence: lifecycle matrix tests and credentialed live
  destroy/readback packet.

### Scenario 6: Missing Live Evidence Blocks Release

- Given: local fixtures pass but Cloudflare credentials or live measurement
  packets are unavailable.
- When: the final release row is evaluated.
- Then: the row remains blocked by external acceptance and the feature remains
  off by default.
- Machine-checkable evidence: Sprint/review status and live-evidence manifest do
  not allow a fixture-only pass.

## Module Behaviors (P0)

### Module 1: Runner Selection and Registry

- Purpose: select an enabled concrete runner after layer/tool policy without
  duplicating run-mode semantics.
- Hard Constraints:
  - Agent Runtime owns the selection contract.
  - Unknown, disabled, incompatible, or unavailable runners fail closed.
  - `workflow` and `service` cannot enter the Agent runner family.
- Recommended Defaults:
  - expose requested/selected runner family, concrete runner ID, route reason,
    and contract version in auditable readback.
  - keep the public product family stable while allowing internal runner IDs to
    evolve through a registered contract.
- Normal path: validate request → select layer → apply tool policy → select
  runner → emit route readback → execute.
- Failure path 1: family unavailable returns structured retryable/blocked state.
- Failure path 2: mode/runner mismatch is rejected before execution.
- Dependencies: Agent Runtime, Worker route adapter, account entitlement.
- Open decisions: strict code representation, resolved in Sprint row 1.

### Module 2: Dedicated Identity and Provisioning

- Purpose: own one durable personal Agent identity/profile per entitled
  user/tenant.
- Hard Constraints:
  - ownership key is stable and tenant scoped;
  - create, retry, disable, re-enable, delete, and expiry are idempotent;
  - upstream identifiers are never public authority;
  - provisioning failure never selects a shared Agent.
- Recommended Defaults:
  - explicit lifecycle state machine and last-error/retry metadata;
  - hash or encrypt upstream identifiers according to existing secret policy.
- Normal path: entitlement check → ownership lookup → idempotent provision →
  persist mapping/audit → expose ready state.
- Failure path 1: partial upstream success reconciles before retry.
- Failure path 2: entitlement removal disables new runs before async deletion.
- Dependencies: account runtime, persistence, secret policy, audit.
- Open decisions: exact persistence schema and upstream API contract.

### Module 3: Ephemeral Sandbox Execution

- Purpose: provide isolated temporary compute below FastClaw.
- Hard Constraints:
  - one run/session owns one sandbox lease;
  - no durable identity or final artifact authority lives in the sandbox;
  - short-lived job token and deny-by-default egress;
  - soft timeout 180 seconds, hard timeout 600 seconds;
  - terminal cleanup is idempotent and observable.
- Recommended Defaults:
  - provider-neutral port in existing Agent Runtime authority;
  - one pinned production-primary backend implementation;
  - raw process output is untrusted and cannot become the final answer directly.
- Normal path: create → configure isolation/token → execute/stream → sync approved
  outputs → destroy → record measured usage.
- Failure path 1: create/exec/stream failure destroys and returns structured
  retryable/blocked state.
- Failure path 2: cancellation/kill interrupts execution, destroys, and records a
  terminal event without fabricated output.
- Dependencies: runner selection, Tool Gateway token, storage, observability.
- Open decisions: final SDK/image pin and measured resource class.

### Module 4: Semantic Events, Evidence, Memory, and Artifacts

- Purpose: translate execution into AiphaBee-owned semantic state and durable
  approved outputs.
- Hard Constraints:
  - event indexes are monotonic per run;
  - raw stdout/stderr and private reasoning are not final user output;
  - evidence/post-check runs before the final answer is visible;
  - memory/artifacts carry owner, hash, classification, size, retention, scan,
    and provenance metadata;
  - cross-tenant reads are denied.
- Recommended Defaults:
  - stream only stable public progress event types;
  - make artifact promotion explicit rather than syncing the whole workspace.
- Failure path 1: artifact scan/size/type failure rejects promotion and still
  destroys the sandbox.
- Failure path 2: incomplete evidence produces partial/blocked output, not an
  unsupported final claim.
- Dependencies: Agent event contract, evidence service, object storage, privacy.
- Open decisions: approved personal-memory categories and retention policy.

### Module 5: Entitlement, Billing, Admin, and Release Evidence

- Purpose: expose product availability and operational control without making
  FastClaw authority public.
- Hard Constraints:
  - entitlement gates availability, not every paid request's route;
  - usage is attributable by run across model/tool/sandbox/storage;
  - operator actions are authorised and audited;
  - live release evidence is separate from fixtures.
- Recommended Defaults:
  - feature off by default until the final release row passes;
  - user sees ready/provisioning/retryable/blocked/disabled states;
  - administrator can retry, disable, delete, and inspect health/audit.
- Failure path 1: billing/entitlement disagreement blocks new personal runs and
  surfaces a supportable state.
- Failure path 2: kill switch blocks new runs and terminates active runs safely.
- Dependencies: account runtime, usage ledger, admin auth, live evidence gates.
- Open decisions: packaging, quota, and user-facing support/refund policy.
